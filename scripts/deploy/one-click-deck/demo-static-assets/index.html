Welcome to your new Decko site

Decko is a card-based web platform: every page on a decko site is a card, cards link to and include each other, and together they form a deck. Abilities beyond the basics — search, formatting, comments, editing tools — come from mods, small packages the engine loads at boot.

This site is a live decko deck served by the decko-ts engine (a TypeScript implementation of decko) running on a Cloudflare Worker with a Cloudflare D1 database. Everything below links into real pages of this deck — click anything.

Try these now

  • Home — the deck's own home card: real content, another card included inside it, and the shape every decko page shares.
  • /_status — the engine and database health check, served as JSON.

A few pages on this demo are machine stress-tests with technical names (like "scale page 173x") — they exist to prove the software handles very large pages, and you can safely ignore them.

How a card works

Every card has a name, a type, and content. Take the deck's real Home card:

  • Its URL is /Home — a card's page lives at its name (longer names like "Scale Page 173x" ride URLs with %20 for the spaces, and the engine resolves each name to a canonical key: home).
  • Its type is Note — the plain-content cardtype.
  • Its raw record is also served as JSON: /Home.json — every card has this machine-readable view.

Cards reference each other two ways, and the Home card shows both:

  • Inclusions — double curly braces: {{Scale Page 1x}} inside Home pulls a whole other card's content into it, the way a dashboard embeds a panel.
  • Links — double square brackets: [[another card]]. This deck even contains a pointer card holding 500 such links, built as a machine stress-test.

And a card's content can be a query instead of prose: a Search-type card holds a one-line search statement and renders the live answer as its page.

Mods: abilities you can add

A mod is a package that plugs set patterns, views, and setting definitions into a running deck — in Ruby decko, a gem whose name starts with card-mod-. This engine ships ports of thirty of them (card-mod-search, card-mod-markdown, card-mod-comment, card-mod-bootstrap, card-mod-help and more), registered by the mod loader in load order when the engine boots.

Adding one: in a Ruby decko deck, you list the card-mod-<name> gem in the deck's Gemfile and boot — the loader picks it up in bundle order. decko-ts ports the same registration mechanism (src/card/mod-loader.ts): a mod declares its set patterns, views, and settings, and the loader wires them in at boot. This demo is a read-only surface, so mods here are part of the deployed engine rather than installable from the browser.

How this site is configured

Two layers, both plain files:

  • decko-config.js — the per-deck runtime config that every card page loads after the script bundle: this site's root URL (decko.rootUrl), the stylesheet path, and the visitor state (decko.signed_in = false — everyone is a read-only visitor here). It lives beside this page in the demo's static assets; edit it and redeploy.
  • The deploy script — scripts/deploy/one-click-deck/one-click-deck.mjs builds and deploys a site like this one. Its default is a dry-run plan; --local runs the same stack on your machine with no Cloudflare account; --cards N sets how many sample cards the seed generates (default 6,200, sized to fit inside Cloudflare D1's free-tier daily write budget); --execute --token <t> --account-id <id> performs the real deploy.

What is real here

The engine is real. Real routing, real rendering, real permission checks, backed by a real Cloudflare D1 database holding 6,241 cards. The content is sample content. Every card in this deck was generated by a script to exercise the read paths at scale — 6,200 Scale Page notes, a 32-deep inclusion chain, a 500-link pointer, a CQL search probe. No real member data exists anywhere in it; every name and sentence is synthetic. Treat it like a showroom floor: a real machine running sample output, safe to wander — the demo is read-only, so nothing here can be edited or broken by visiting.

Want your own content here?

This sample deck was generated by scripts/deploy/one-click-deck/seed-fitting-scale.mjs (the --cards flag sets the scale). To put a real deck here instead, the import tool tools/migrate/import-deck.mjs accepts any of three source formats:

  • --source <deck.sqlite> — a decko SQLite database file,
  • --dump <dump.sql> — a mysqldump-style SQL text dump of a deck,
  • --seed <seed.sql> — a plain file of SQL INSERT statements.

It validates the source, maps it onto the schema, and emits D1-ready chunks your Worker can serve.
