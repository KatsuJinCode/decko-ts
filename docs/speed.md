# Speed: the port against Ruby Decko

Generated by `benchmarks/speed/render-docs.mjs` from the run record `benchmarks/speed/runs/2026-10-14-synthetic-v1.json` (measured 2026-10-14, commit 0690f591b9, with uncommitted changes). Every number below is from that file.

## What was measured

The same 7 pages of the synthetic-v1 deck (`reference-harness/fixtures/synthetic-v1`), requested anonymously: `/`, `/Note_001`, `/Note_037`, `/Decko_Bot`, `/RichText`, `/Cards_with_accounts`, `/Search`.

Three servers, each on its own copy of the deck:

- **Ruby Decko 0.20.0** (card 1.110.0), the stock oracle app (`reference-harness/oracle/app`) under Puma in production mode, through `benchmarks/speed/ruby/config.ru`.
- **The port's Node host** (`benchmarks/speed/node-host.ts`): the edge deck boot and edge request handler over node:sqlite.
- **The port in workerd** (`benchmarks/speed/worker-entry.ts`, built with the deploy bundle's esbuild settings) over a local D1 in Miniflare: Cloudflare's runtime and Cloudflare's database API, on this machine.

One client (node fetch (undici), keep-alive, sequential for cold/warm; Node v24.19.0) on the same machine (Intel(R) Core(TM) i7-14700F, 28 logical CPUs, 32 GB, win32). For each server:

- **first request**: the first request after the server listens (for the port, the deck boot).
- **cold**: each page once, the first time it is asked for.
- **warm**: each page 20 times in sequence; p50 and p95.
- **throughput**: 8 concurrent clients cycling through the pages for 10 s.

**Simulated database distance.** At the edge the application runs near the visitor and the database does not, so every database round trip crosses a network. Each server holds every round trip a fixed time before it is sent: the port per driver call (a batch of statements is one trip, as on D1 and libSQL), Ruby per SQL statement ActiveRecord sends. `trips` is the count each server reports in `X-Decko-Db-Trips`. Hop 0 is a database on the same machine.

## Bytes served

The Node host and the workerd Worker served byte-identical bodies on every page, at every hop (sha256 with the per-render `data-slot-id` masked, recorded per page in the run record).

Ruby here runs in production mode, whose pages differ from the development-mode captures the parity grade compares against (asset links and the production head, for example), so its byte counts are not the port's. Rendering parity is measured separately: `reference-harness/grade-reports/` and `docs/parity-method.md`.

## Reproduce

```
npm ci --ignore-scripts          # the port needs no native addon here (node:sqlite)
node benchmarks/speed/build.mjs
# Ruby: GEM_HOME/GEM_PATH must hold the gems of benchmarks/speed/ruby/Gemfile.lock
#   (the oracle's gems plus Puma: gem install puma; bundle install)
node benchmarks/speed/run.mjs --targets ruby,node,workerd --hops 0,10 --warm 20 --duration 10 --concurrency 8 --out benchmarks/speed/runs/2026-10-14-synthetic-v1.json
node benchmarks/speed/render-docs.mjs benchmarks/speed/runs/2026-10-14-synthetic-v1.json
```

## Running it against a hosted edge

The same client measures a deployed Worker or edge script with `--url name=<base url>` (repeatable; no hop is simulated, the network is real). The deck must be synthetic-v1:

```
# Cloudflare: the Worker of benchmarks/speed/worker-entry.ts over a D1 holding synthetic-v1
npx wrangler d1 create decko-speed
npx wrangler d1 execute decko-speed --remote --file <synthetic-v1 deck dumped as SQL>
npx wrangler deploy tmp/speed/worker.mjs --name decko-speed --compatibility-date 2026-09-01 \
  --compatibility-flags nodejs_compat --no-bundle    # with the D1 binding DB in its wrangler config
node benchmarks/speed/run.mjs --url cloudflare=https://decko-speed.<account>.workers.dev \
  --url bunny=https://<pull zone>.b-cdn.net --warm 20 --duration 10 --concurrency 8
```

A hosted run spends the account's request and database quota; it is not run by this repository's tests.
